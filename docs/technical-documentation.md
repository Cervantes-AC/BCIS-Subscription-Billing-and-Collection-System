# Technical Documentation

## System overview

BCIS is a Windows desktop client built with Electron, React, and TypeScript. The renderer communicates with a Fastify REST API over HTTP; the API is the only application component that connects to PostgreSQL. Drizzle ORM defines the schema and runs SQL migrations. Reports are generated by the API as XLSX or PDF files.

```text
Windows PC 1 ─┐
Windows PC 2 ─┼─ LAN/HTTP ─> Fastify API ─> PostgreSQL
Windows PC 3 ─┘                  ├───────> Attachments
                                 └───────> pg_dump backups
```

The API defaults to `0.0.0.0:3000`. The desktop API URL is configured at build time with `VITE_API_URL`; the API origin allowlist is configured with comma-separated `CORS_ORIGIN` values.

## Package map

| Package | Responsibility |
| --- | --- |
| `packages/shared` | Shared TypeScript types, Zod request schemas, and centavo currency utilities |
| `packages/db` | PostgreSQL connection pool, Drizzle schema, migrations, and deterministic/demo seeds |
| `packages/api` | Authentication, authorization, validation, business services, audit records, and report endpoints |
| `packages/desktop` | Electron main/preload boundary and React operational screens |

## Data model

The Drizzle schema covers users, roles, permissions, sessions, subscribers and addresses/contacts, plans, service accounts and service history, billing cycles, invoices and invoice items, adjustments, payments and allocations, payment proof and reversals, GCash verification, collection areas and assignments, collection batches and batch accounts, remittances, suspension/reconnection records, receipts, audit logs, application settings, and backup history. Foreign keys preserve ownership; unique indexes protect account, receipt, billing-cycle, and GCash-reference identities. See `packages/db/src/schema` and `packages/db/drizzle` for the authoritative definitions and SQL migration.

## Financial rules

- Monetary values are stored and sent as integer centavos. The shared utilities convert pesos for display and input.
- Billing is generated per active service account and billing cycle. A unique database index rejects a duplicate invoice for the same pair.
- Automatic payment allocation orders open invoices by due date and applies the payment to the oldest balance first.
- GCash submissions remain pending until an authorized user verifies them; a proof image alone does not post a payment.
- Posted payment corrections use a reversal record and a linked negative payment. The original receipt/payment remains available for audit.
- Collection batches retain expected and actual cash/non-cash figures. A reconciled shortage prevents batch closure.

## API and authorization

The API is versioned under `/api/v1`; `/health` provides a process health check and `/documentation` exposes Swagger in development. Route schemas use shared Zod definitions. Each protected route calls `fastify.authorize(permissionCode)`; renderer button visibility is not the security boundary. The seed creates the system roles and grants permissions.

Key route groups include `/auth`, `/subscribers`, `/plans`, `/service-accounts`, `/billing-cycles`, `/invoices`, `/payments`, `/gcash`, `/collection-areas`, `/collection-batches`, `/receivables`, `/reports`, and `/admin`.

## Electron security

The main process owns window and operating-system APIs. The renderer uses a preload bridge with context isolation enabled and Node integration disabled. Never place database credentials in the renderer or ship a direct PostgreSQL connection string in the desktop bundle. Use HTTPS/VPN or a trusted isolated LAN when moving beyond a classroom network.

## Backup and recovery

The Admin backup screen calls API endpoints that invoke PostgreSQL dump/restore tools on the server. Install matching PostgreSQL client tools on the API host, secure the backup directory, and keep a second copy on a separate device. A successful backup is not proof of recoverability: restore to a disposable database and compare row counts/checksums before relying on it. See [the deployment guide](deployment-guide.md).

## Known validation boundaries

Concurrent use from separate physical PCs, backup restore, and report output depend on a reachable PostgreSQL instance and Windows LAN clients. These must be demonstrated in the target lab network; a local build alone does not certify those deployment conditions. The automated acceptance suite and its execution instructions are in `tests/acceptance/`.
